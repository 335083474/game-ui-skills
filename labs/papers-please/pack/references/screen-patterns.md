# Screen patterns

These are task layouts and interaction contracts, not finished screens. Share one invented visitor, policy set, and household ledger across the three views.

## Inspection

Keep a foremost travel document on a narrow desk surface. A second document may sit partly beneath it. Provide a compact tool row for compare / inspect / stamp and a short rule excerpt that can be expanded. The user must be able to choose a field, compare the visible values, and see a named discrepancy before deciding. Present two explicit outcomes; require confirmation before the decision is committed. A failed comparison should identify the field and values in text. Never rely solely on a red border. Pointer and keyboard activation should resolve the same field and outcome.

Synthetic example: an invented traveler has a valid entry date but a mismatched permit district. “District” is highlighted with both values printed beside it. The decision remains pending until a stamp is chosen.

## Rulebook

Use page tabs or an index strip on a bound rulebook. Each page contains one policy group, an effective date, and short actionable rules. Keep the page content in a readable line length with field names in a consistent column. The current page indicator remains visible when switching policies. Search may reveal matching clauses; it does not change the inspection state. Provide previous / next page controls with disabled boundaries and keyboard focus. Avoid turning every rule into an alert card.

Synthetic example: the “Permit” page lists three checks—district, expiration, and issuing office—using invented policy text. Opening the page does not alter the case.

## Daily ledger

Present the day's wages and expenses as a narrow ruled statement: income at the top, deductions below, and remaining balance at the bottom. Keep currency and sign conventions visible. Expand a household line only when the user inspects its detail; do not decorate expense rows as equal-weight tiles. Settling the day applies the displayed arithmetic once, then marks the statement closed. A reset, if requested, must be an explicit demo reset rather than an implied real save.

Synthetic example: wages 70, rent 20, food 15, heat 5, medicine 0, remaining 30. These invented figures are only a coherent UI sample; keep zero as an explicit sample amount rather than an unknown field.
